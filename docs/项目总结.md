## 一、项目背景与目标

景区导览长期依赖人工讲解与固定指示牌：讲解员排班有限、高峰期接待不过来，游客想了解某个景点的历史与看点，往往只能靠文字牌或自己搜索。本项目把「数字人 + 大语言模型」落到景区导览场景，做一套**以大屏交互终端为载体、以语音为主要入口**的 AI 导览系统。

围绕这个目标，项目要解决四件事：

1. **让游客用说话就能问**——自然语音提问，系统给出景点讲解、路线推荐等回答；
2. **让回答有形象**——不只是文字和语音，而是由数字人"讲"出来；
3. **让运营方能管**——景点、知识库、数字人形象、游客与数据都要能在后台维护；
4. **尽量不挑硬件**——不能假设每台终端都配了独立显卡。

## 二、系统架构

系统采用**四层分工**，把交互、业务、AI 编排、模型推理拆开，任何一层都能独立替换或扩容：

```
┌─────────────────────────────────────────────────────────────┐
│  交互层   web-kiosk 大屏终端 │ web-admin 管理后台 │ mobile-app 移动端  │
├─────────────────────────────────────────────────────────────┤
│  业务层   Spring Boot + MyBatis-Plus + JWT                   │
│           认证 / 景点 / 用户 / 会话 / 反馈 / 埋点统计             │
├─────────────────────────────────────────────────────────────┤
│  AI 编排层 FastAPI                                            │
│           意图理解与回复生成 · RAG 检索 · 语音识别与合成 · 数字人调度   │
├─────────────────────────────────────────────────────────────┤
│  引擎层   SadTalker │ Wav2Lip │ MuseTalk（各自独立 HTTP 服务）    │
├─────────────────────────────────────────────────────────────┤
│  存储层   MySQL（业务） │ Redis（缓存/会话） │ Chroma（向量知识库）   │
└─────────────────────────────────────────────────────────────┘
```

选择这套分层的原因很直接：数字人引擎是 Python 生态、依赖重、启动慢，而业务逻辑更适合 Java；把推理单独做成服务后，Java 侧只通过 HTTP 调用，引擎换掉不影响业务代码。

## 三、核心设计与亮点

### 3.1 双引擎 + 四级降级（本项目最重要的设计）

数字人项目最常见的坑是"默认用户有一块好显卡"。本项目不接受这个前提，把数字人输出做成**可以逐级降下来的四档**：

| 档位 | 引擎 | 特点 | 运行位置 |
| --- | --- | --- | --- |
| 第一档 | SadTalker | 一张图生成说话视频，表情与头部动作最自然 | 服务端（GPU） |
| 第二档 | Wav2Lip | 只做口型对齐，配预置待机视频当底板，资源占用显著降低 | 服务端（GPU） |
| 第三档 | Live2D | 漫画风人物，不依赖 GPU | 服务端 / 前端 |
| 第四档 | CSS Q 版人物 | 前端兜底，语音照播、讲解内容不减，仅不做口型同步 | 前端 |

**降级判据有两套**：一是**环境有没有 GPU**，决定从哪一档起步；二是**运行时负载**，决定要不要继续往下降。前三档在服务端、第四档在前端自救，所以严格说是覆盖整条链路的四级降级。这套链路还有第二个用途：**它在流量高峰期同时充当服务端过载保护**，负载上来时主动切到轻量引擎，保证导览不中断。

需要说明的是，切到 Wav2Lip 之后**仍然走 GPU，只是模型轻很多**，同一张卡能承载的并发明显提升；真正完全不吃 GPU 的是 Live2D 与 CSS 两档。

### 3.2 语音交互闭环

把链路串成一条完整闭环：**语音输入（ASR）→ 大模型理解与生成 → 语音合成（TTS）→ 音频驱动数字人视频**。前端的 `useDigitalHumanChat` / `useDigitalHumanStream` 两个组合式函数负责与编排服务对接，支持流式返回，避免游客长时间等待。

### 3.3 RAG 知识库，让回答有依据

景点讲解属于"必须准确"的场景，不能靠模型自由发挥。项目把景区资料整理为结构化数据集与讲解词，切分后写入 Chroma 向量库，提问时先检索再生成，降低幻觉；后台可对知识库内容做增删改查与重新索引。

### 3.4 GPU 版与无 GPU 版双形态

代码库中同时维护了 `scenic-guide-ai`（GPU 部署）与 `scenic-guide-ai-nogpu`（无 GPU 部署）两套形态：前者接三套数字人引擎，后者只用 Live2D / CSS 两档，可跑在普通服务器甚至展厅小主机上。

### 3.5 管理后台

后台共规划 8 个功能视图：数据看板、景点管理、2D 地图坐标、知识库、数字人形象配置、游客管理、用户管理、投诉反馈、数据分析，覆盖从内容维护到运营分析的全流程。

## 四、技术难点与解决思路

| 难点 | 解决方式 |
| --- | --- |
| 三套引擎接口风格各异、调用方式不统一 | 各自封装为独立 HTTP 服务（`sadtalker_api.py` / `wav2lip_api.py` / `musetalk_api.py`），对外暴露统一协议，详见 `数字人接口协议.md` |
| 数字人视频生成耗时较长 | 采用"预置待机视频 + 口型对齐"的轻量路线作为主力档位；同时用降级链路保证等待期间服务不中断 |
| 大屏端地图与景点坐标对齐困难 | 前端实现 2D 景区地图与百度实景街景两种视图，统一坐标转换工具（`coordTransform`）处理不同坐标系差异 |
| 服务多、端口多、部署繁琐 | Docker Compose 统一编排，端口集中分配并写入 `docs/端口分配文档.txt`，一条命令拉起全栈 |
| 语音链路依赖多、排障困难 | 语音能力收敛到独立的 `voice_service`，接口与错误码写入协议文档，便于定位 |
| 业务数据与 AI 服务的数据边界 | 业务数据留在 MySQL 由 Spring Boot 管理，AI 侧只处理推理与检索，职责不交叉 |

## 五、个人承担的工作

- **架构设计**：确定四层分工与"编排服务独立"的方案，定义业务后端与 AI 服务之间的接口边界；
- **引擎选型**：对比 SadTalker、Wav2Lip、MuseTalk 三套引擎的效果与资源占用，设计四级降级链路与切换判据；
- **接口定义与联调**：编写数字人接口协议，打通前端 → 业务后端 → 编排服务 → 引擎的完整调用链；
- **前端开发**：大屏终端（对话、数字人、2D 地图、实景街景、天气）、管理后台、移动端三个前端的页面与接口联调；
- **部署方案**：GPU 与无 GPU 两套 Docker Compose 编排、端口规划与部署手册整理；
- **排障与文档**：定位联调阶段的接口与坐标类问题，整理系统设计文档、部署手册、接口协议等资料。

**开发方式说明**：本项目主体代码由 AI 编程智能体完成，本人负责架构设计、引擎选型、接口定义、联调排障与验收测试。实践中一个很深的体会是：**AI 在前期功能开发阶段效率极高，但到了"更换引擎架构、引入复杂功能"的改动阶段，编码质量会明显下滑**，判断原因是上下文压缩导致早期细节丢失——因此关键架构改动坚持人工把控。

## 六、项目成果

1. **一套可运行的系统**：三个前端 + Spring Boot 业务后端 + FastAPI 编排服务 + 三套数字人引擎，支持 GPU 与无 GPU 两种部署形态；
2. **一条四级降级链路**：让数字人导览在从独立显卡到普通办公机的各种硬件上都能交付；
3. **一套完整的运营后台**：知识库、景点、形象、用户、反馈、数据可视化；
4. **一批工程文档**：系统设计文档、部署手册、端口分配文档、数字人接口协议、PPT 大纲；
5. **数据资产**：灵山胜境景点结构化数据集、景区历史文化与游览指南、景区旅游数据行为分析数据；
6. **代码已开源**：341 个文件（不含模型权重与第三方引擎源码）托管于 GitHub。

## 七、心得与不足

**收获：**

- **分层是复杂系统能维护的前提**。把引擎、编排、业务、交互拆开后，换引擎不用动业务代码，前端也能独立推进；
- **降级不是妥协，而是交付保证**。与其做一个"只在开发机上好看"的数字人，不如做一个"在任何机器上都能用"的导览系统；
- **接口先行**。三套引擎能被统一调度，靠的是先把协议定下来再写实现。

**不足与改进方向：**

- 目前**缺少量化的性能数据**（并发上限、首帧耗时、降级切换耗时、语音识别准确率），后续需要压测补齐，用数据支撑设计结论；
- Live2D 与 CSS 两档牺牲了口型同步，观感与真实数字人差距明显，需要更自然的兜底方案；
- RAG 的效果高度依赖文档切分策略，当前策略还比较粗糙，需要针对景点讲解语料做调优；
- 工程化程度不足：**缺少自动化测试与 CI**，回归主要依靠人工验证；
- 多引擎同时在线时的资源调度（显存分配、排队策略）还没有做精细化管理。
